********************************* A. DESKTOP APPLICATION LIFECYCLE *********************************

--> What Is A Desktop Application?
	A desktop application is a program that runs as a process under the Operating System (such as Windows, Linux, or macOS) and provides a Graphical User Interface (GUI) through which the user interacts with the application.
	
	A desktop application is ultimately a program that the Operating System starts and manages.
	Not every desktop application must have a GUI. Console applications can also run as processes on a desktop Operating System.
	
--> Desktop Application Lifecycle
	User	->	Double Clicks EXE	->	Windows Operating System	->	Loads EXE into RAM	->	Creates Process	->	Initializes Process Resources	->	Starts Primary Thread	->	Transfers Execution to Entry Point	->	main() Executes

--> Desktop Application Startup Flow : 

	Step 1 : User Starts The Application
		The user double-clicks an executable (.exe) file.
		The double-click is received by the Windows Operating System, not by the application.
		The application is not running, No Process Exist, No Window Exist yet.

		--> What Is An Executable (.exe)?	
			An Executable (EXE) is a file that contains	:	Machine instructions	|	Program code	|	Static data	|	Information required by the operating system to load the program
			An EXE is not a running program.It is simply a file stored on secondary storage.
			
	Step 2 : Windows Loads The Executable into RAM
		Windows identifies the .exe file as an executable program.
		Windows prepares the executable and required libraries in the process's virtual address space.

		Reason:
			The CPU executes instructions through memory, while the Operating System manages how program code and data are mapped into the process's address space.

	Step 3 : Windows Creates A Process
		An executable (.exe) is only a file stored on disk. It is NOT a running program.
		
		When Windows starts the executable, it creates a Process.
			Think:
				EXE       -> Blueprint
				Process   -> Running Program
		
		A Process is a running instance of a program. During process creation Windows initializes :  Program Code | Stack | Heap | Global Variables | Primary Thread | Handles | Environment
		These are runtime resources associated with the process. They are not already-created runtime objects stored inside the EXE.
		They are created only when the process starts.
	
	Step 4 : Windows Transfers Control To The Entry Point
		After the process is initialized, execution eventually reaches the program's entry point.
		For a Kotlin/JVM Desktop application, execution eventually reaches:
			fun main(args: Array<String>)
			
		At this stage:

			✓ Process is running.
			✓ main() is executing.
			* window not exist

		However, No graphical window exists yet.

		Reason : The program has not requested the operating system to create a window.
		
==> SUMMARY OF CHAPTER 1 :
		User		->		Starts EXE		->		Windows Operating System		->		Loads EXE into RAM		->		Creates Process		->		
																																					|
																																					|
																																					↓						
		No Window Exists Yet		<-		main() Starts Executing		<-		Transfers Execution to Entry Point		<-		Initializes[Program Code / Stack / Heap / Global Variables / Primary Thread / Handles / Environment Information]
						
			
********************************* B. WINDOWING SYSTEM *********************************

--> What Is A Windowing System?
		It is a part of the Operating System for creating and managing graphical windows.
		
		Responsible  : Creating Window | Showing Window | Moving Window | Resizing Window | Closing Window | Mouse Events | Keyboard Events

--> Does Every Process Have A Window?	-   NO.

    Reason : Not every application requires a GUI.
		Examples : Git | Compiler | Ping | CMake

    Rule : A process does NOT automatically get a Window.The application must request the Operating System/windowing system to create one.

--> Who Creates The Window?
		Application does NOT create the Window.
		
		Flow : Application -> Windows API -> Windowing System -> Native Window Created
			
--> Windows API
		The Operating System exposes functions that applications use to communicate with Windows.
			Examples : CreateWindow() | DestroyWindow() | ShowWindow() | MoveWindow() 
			
		Think : Windows API = Interface through which applications/frameworks request Operating System functionality.
		
--> Native Window
	The actual desktop window is an OS-managed native window.
	The application/framework requests the Operating System to create it and can then interact with it through platform APIs.

--> Window Handle (HWND)
		Windows identifies a native window using a handle.
		It is commonly represented by HWND in Win32 programming.

		Applications use this handle whenever they want Windows to perform another operation.
		Example : HWND	->	MoveWindow()
		
		Think :  HWND = Window ID / Window Reference

--> Why Doesn't Windows Return The Actual Window?
	Applications interact with the native window through an OS-defined handle/API instead of directly manipulating the Operating System's internal window object.

	This protects the Operating System's internal implementation and prevents applications from directly modifying its internal structures.


--> Event Driven Programming
	Console programs execute sequentially.
		Example Console Application Works : Step 1 -> Step 2 -> Step 3 -> Exit

    Desktop Application : User interaction can determine when different actions occur.
		Example : Click Button | Press Key | Resize Window | Move Window


--> What Is An Event?
	An Event is an action or occurrence that the application can respond to while it is running.
		Examples	:	Mouse Click		|	Mouse Move

		
--> Message Queue
		Windows receives hardware/input events.
		Examples : Mouse Click | Keyboard Press | Window Resize

    Windows delivers relevant events to applications through messages/events.
	These messages can be queued and processed by the application.

--> Message Flow
		User Clicks Mouse -> Windows OS Detects Event -> Creates/Dispatches Message -> Application Receives Message -> Processes Message

--> Message Loop
	Desktop applications need to continue running and process incoming events after creating a window.
	A traditional Windows desktop application uses a Message Loop to continuously retrieve and process messages.

********************************* C. WHY DO WE NEED A UI FRAMEWORK? *********************************

--> Why WE need Compose(framework) if Windows(OS) already provides API like : CreateWindow(), ShowWindow(), MoveWindow() becuase We can directly use that API into our Kotlin Application 
		
		1. A UI Framework does not replace the Operating System. It provides a higher-level abstraction over low-level APIs.
		2. Windows already provides the fundamental capabilities. Compose provides a much easier and more organized programming model for using those capabilities.
		3. A UI Framework reduces the amount of platform-specific and repetitive code developers need to write.

		Example without Compose :	Create Button | Set Width  | Set Height | Set Font | Set X Position | Set Y Position		Lots of Works
		
		Example of Compose 		:	
					Button(	
						modifier = Modifier.padding(16.dp)
					)
			Compose handles many UI concerns such as : Layout | Measurement | Drawing | Input/Event Handling | UI Updates
	
			Compose does not replace the Operating System.
			For a desktop application, the framework ultimately integrates with the platform's native windowing system.

		
--> Compose was created because writing directly with low-level APIs becomes:
		Too much code	|	Difficult to maintain	|	Difficult to adapt to different screen sizes	|	Difficult to reuse UI components
		
--> Can Kotlin Create UI?		-	   NO.
		Kotlin is only a programming language, not a UI toolkit.
		
		Kotlin provides 				:  Variables | Functions | Classes | Coroutines | Collections 
		It does NOT itself provide		:  Window |  Button | TextField | Image | Row | Column

		To create Desktop UI, Kotlin can use: : Compose Desktop / JavaFX / Swing

--> Can C++ Create UI?		-	   NO.
	
	C++ is a programming language.
	C++ applications also require a UI technology/framework or platform API.

	Examples	:	Win32 API | MFC | Qt | wxWidgets
		
--> Problems with Win32 API
		Win32 API is a low-level API. It provides maximum control but requires a large amount of manual work.
		Every Windows desktop application ultimately depends on it (directly or indirectly).
		
		We have to manually : Create Window | Create Label | Create TextBox | Create Password Box
		
		Main Problem :  Too much Boilerplate Code. | Manual X,Y Positioning | Difficult Maintenance. |  Manual Message Handling. | Platform Dependent (Windows Only)
		
--> Why Do We Need A UI Framework?
		Instead of working directly with low-level APIs, developers use a UI Framework.
		
		Instead of writing low-level code, it provides high-level components and abstractions.
			Examples :  Window |   Button |  Text |   TextField |  Image |  Menu
			
--> Responsibilities Of UI Framework
	A UI Framework provides high-level components and hides platform-specific implementation.

	Responsibilities : Create UI Components.  | Manage Layout | Handle Events |  Draw UI |  Manage UI State | Hide Platform Specific APIs
	
--> Does A UI Framework Replace The Operating System?		-	No
	The Operating System still provides : Native Windows	|	Mouse Events	|	Keyboard Events
	The framework communicates with the Operating System and provides a higher-level API to the application developer.

********************************* A. WHAT EXACTLY IS COMPOSE MULTIPLATFORM *********************************

What is a Framework? 	-	A framework is a collection of pre-written code, libraries, and rules that helps you build applications faster.
	Examples: Kotlin
				│
				├── Jetpack Compose (Android UI Framework)
				├── Compose Multiplatform (Cross-platform UI Framework)
				├── Ktor (Backend Framework)
				└── Spring Boot (Backend Framework for Java/Kotlin)

--> What is Compose Multiplatform
	
	Compose Multiplatform is a modern declarative UI framework developed by JetBrains.
	It allows developers to build user interfaces using Kotlin and share UI code across multiple supported platforms.
	Instead of creating completely separate UI implementations for each platform, we can share a large portion of the UI code.

	Conceptually:

		Kotlin + Compose Multiplatform
					↓
			Shared UI Code
					↓
			┌─────────┼─────────┐
			↓         ↓         ↓
		Android    Desktop     iOS
			↓         ↓         ↓
		Platform-specific implementation underneath
	
	Compose Multiplatform does NOT mean that every platform internally works exactly the same way.
	The goal is to share UI/application code while Compose and the platform integration handle the differences underneath.

		
--> What Is A UI Toolkit?
	A UI Toolkit is a collection of APIs and components used to build graphical user interfaces.

	It usually provides things such as : Text | Button | TextField | Image | Layout | Input Handling | Styling | Rendering

	Example : Compose	|	JavaFX	|	Swing	|	Qt

	Think : UI Toolkit = Tools used to build UI.
	
	
--> UI Toolkit vs UI Framework
	
	A UI Toolkit mainly provides reusable UI components.
	A UI Framework provides : UI Components | Architecture | Rules | Runtime | State Management | Event Handling | Layout System

	Compose Multiplatform provides all of these.


--> Compose Multiplatform vs Jetpack Compose

	Jetpack Compose:

		• Developed by Google.	|	• Primarily designed for Android UI.	|	• Uses Kotlin.	|	• Provides a declarative UI programming model.

	Compose Multiplatform:

		• Developed and maintained by JetBrains.	|	• Builds on the Compose programming model.	|	• Extends Compose UI development to multiple platforms.
		• Uses Kotlin.	|	• Allows UI code to be shared across supported platforms.

	Think:
		Jetpack Compose			->			Android-focused

		Compose Multiplatform	->			Multiplatform UI

--> Why JetBrains created Compose Multiplatform?

	Developers often want to build applications for multiple platforms without writing the entire UI separately for each platform.

	Without shared UI:
		Android UI	->	Separate Code
		Desktop UI	->	Separate Code
		iOS UI		->	Separate Code

	With Compose Multiplatform:
		Shared Compose UI	->		Multiple Platforms

--> Compose Multiplatform Targets

	Compose Multiplatform supports UI development for multiple platforms.
	Common targets include : Android	|	Desktop	|	iOS		|	Web
	
--> Desktop Target
	Compose Multiplatform can be used to create desktop applications.

	Supported desktop operating systems include : 	Windows | Linux | macOS

	Our application will primarily use : Compose Multiplatform	->	JVM/Desktop	->	Windows

--> Android Target
	Compose Multiplatform can share UI code with Android applications.

	Conceptually:
		Shared Compose UI	->	Android Platform	->	Android Application


--> Shared UI Concept
	Shared UI means that the same Compose UI code can be used across multiple platforms.

	Example:

		@Composable
		fun LoginScreen() {
			Column {
				Text("Login")
				Button(
					onClick = { }
				) {
					Text("Login")
				}
			}
		}

	The same UI function can potentially be used by multiple supported platforms.

	Conceptually:
		LoginScreen()	->		Shared Compose UI	->		Android / Desktop / iOS


	Important:
		Shared does NOT mean that every single line of application code must be shared.
		Platform-specific code may still be required when interacting with platform-specific APIs.

--> Platform-specific UI Concept
	Some functionality depends on the platform.

	Example:
		Windows-specific API	|	Android-specific API	|	iOS-specific API

	In such cases we can keep the platform-specific implementation separate.

	Conceptually:
		Shared Code
			│
			├── Common UI
			│
			└── Platform-specific Code
					├── Android
					├── Desktop
					└── iOS

	Example:
		Shared:
			LoginScreen
			HomeScreen
			Button
			Text
			Layout

		Platform-specific:
			Windows API
			Android API
			iOS API
			
--> Declarative UI	vs Imperative UI

	Declarative means : 
		Describe what the UI should look like.
			Example : Text("Hello")
	
		We are simply describing the UI.Compose decides : Size | Drawing | Rendering | Updating
		
		Flow : State Changes	->	Compose Detects Change	->	Recomposition	->	Updated UI
		
	Imperative means : 
		Imperative UI means we explicitly tell the UI system HOW to perform operations.
		Example : Suppose I want a Login Button
			So we explained every step to Framework like : Create Window -> Create Button -> Set Width -> Set Height -> Set Color -> Set Position -> Draw Button
		
		Exampele : User Clickk		->		Increase countk		->		Find TextViewk		->		Convert Int → Stringk		->		Set Textk		->		Refresh UI
	
	--> Why Did Google Choose Declarative UI?
		Modern applications constantly change.Updating every UI component manually becomes difficult.
		Frameworks like Compose automatically update the UI whenever the application's State changes.his makes applications : Easier to write | Easier to maintain

--> Why Is Compose Called Declarative?
		Compose follows the Declarative UI approach.The developer describes what the UI should look like.Compose decides how to create and update that UI.

--> application()
	application() is a Function provided by Compose Multiplatform.
	It is the Entry Point into the Compose Framework.
	Example :
		fun main() = application {
		}
	This is equivalent to :
		fun main(): Unit {
			return application {
			}
		}
	
	When Windows starts our application : 	
		Windows OS ->	Process	->	JVM	->	main() -> application()
		
		At the point main() starts: 
			✓ Process exists
			✓ JVM is running 
			✓ main() is executing 
			✗ Compose Desktop UI has not been created yet 
			✗ Native application Window has not been created yet
	
	So Who is responsible for starting the Compose environment?			-	Compose Multiplatform	
	It cannot be : Windows OS | Kotlin | JVM
		
		
	1 -  
		fun main(args: Array<String>)
		Meaning:
			Function Name → main	|	Parameter → args	|	Return Type → Unit (implicit)
		Equivalent to :
			fun main(args: Array<String>): Unit
	
	2 — Expression Body (=)
		means:
			fun main(args: Array<String>): Unit {
				return application {

				}
			}
		because in Kotlin :
			fun add(a: Int, b: Int): Int {
				return a + b
			}
			fun add(a: Int, b: Int): Int = a + b						//Expression Body Functions

		
	3 — Why application { } ?
		Conceptually :
			fun application(
				content: () -> Unit
			)

		application() accepts a Function as its parameter.
		So application() is a Higher Order Function.
	
	5 — Trailing Lambda
		application {
			// Your code				//The lambda[code inside {} ] contains the code that Compose will execute AFTER it initializes the Compose Runtime.
		}

	Responsibility : 
		application()
			↓
		Initialize Compose Runtime
			↓
		Prepare Compose Environment
			↓
		Execute the Lambda

--> Role of application()
	application() provides the Compose Desktop application environment and manages the desktop application's lifecycle.

	Inside application(), we can create one or more Compose Windows.

	Example :
		fun main() = application {

			Window(
				onCloseRequest = ::exitApplication
			) {

				App()

			}
		}


	Conceptually :
		main()
		  ↓
		application()
		  ↓
		Window()
		  ↓
		Compose UI
	
	application() is also a Higher-Order Function because it accepts a lambda containing the application's Compose code.
	Example : 
		application { 
			// Compose Desktop application code 
		} 
	The code inside { } is the lambda passed to application().
	
--> Window()
	Window() is a function provided by Compose Multiplatform for creating and configuring a Desktop Window.
	It is also a Higher Order Function because its LAST parameter is a Lambda.
	
	Example :
		Window(
			onCloseRequest = app::onDestroy,
			title = "ATEK GATE",
			state = rememberWindowState(
				placement = WindowPlacement.Fullscreen
			)
		) {
			App(app)
		}
	
		Window() also accepts a lambda as its content. 
		The lambda describes the Compose UI that should be displayed inside the Window.
		
	--> Role of Window()
		Window() connects the Compose application with the platform's Desktop Windowing System.

		Conceptually :
			Window()
				↓
			Platform Windowing System
				↓
			Operating System
				↓
			Native Desktop Window

		Important :
			Compose does not replace the Operating System's Windowing System.
			The actual native Desktop Window is ultimately created and managed through the platform's windowing system.
			Window() provides the Compose API through which our application configures and hosts UI in that Desktop Window.

		Example :
			Window {
				App()
			}

		Meaning :
			Create/configure a Desktop Window
					+
			Display App() as the Compose content inside it.
		
	--> Why Does Window() Accept a Lambda?
		Window() needs to know what Compose UI should be displayed inside the Window.

		So we provide the UI as a lambda.

		Example :
			Window {
				App()
			}

		The lambda:
			{
				App()
			}

		describes the Compose content of the Window.
		
		Think : 
			Window() -> Where the UI is displayed 
			Lambda -> What UI is displayed


--> Scene()
	Scene is an internal architectural concept used by Compose Desktop.
	After the Desktop Window is created, Compose needs an environment in which it can manage and render the Compose UI associated with that Window. 
	This Compose-managed environment is referred to as a Scene.
	
	Conceptually : Native Desktop Window -> Compose Scene -> Compose UI -> App() -> Composable Functions
	
	EXAMPLE: 
		+-----------------+
		| ATEK GATE  X    |
		+-----------------+
		| +-----------+   |
		| |           |   |
		| |    Scene  |   |
		| +-----------+   |
		+-----------------+
 
	--> What lives inside the Scene?
		App()	|	MainScreen()	|	Buttons() |  Text()  |  Images
		
	--> Why do we need Scene?
		The Native Window is responsible for the platform-level Window.
		Compose is responsible for managing and rendering the Compose UI.
		The Scene provides the connection/environment between these two layers.
		
--> Relationship between application(), Window(), Scene and UI

	Complete structure :

		fun main() = application {
			Window(
				onCloseRequest = ::exitApplication
			) {
				App()
			}
		}


	Conceptual flow :
		main()	->	application()	->	Window()	->	Native Desktop Window	->		Compose Scene	->	App()	->	Composable UI


	Each part has a different responsibility :

		main()					→ Application Entry Point
		application()			→ Compose Desktop Application Environment / Lifecycle
		Window()				→ Desktop Window Configuration and Compose Content Host
		Scene					→ Compose-managed environment connecting the native window with Compose UI
		App()					→ Application's UI Root
		Composable Functions	→ Describe individual pieces of UI


********************************* C. COMPOSE MENTAL MODEL *********************************			

--> What is a Composable?
	A Composable is a function that participates in Compose's UI composition system.
	It describes a piece of UI or UI-related behavior.

	Example:
		@Composable
		fun Greeting() {
			Text("Hello")
		}


	Think : Composable = A building block of Compose UI.


--> Composable Function
	A Composable Function is a Kotlin function marked with @Composable.

	Example: 
		@Composable
		fun MainScreen() {
		Text("Welcome")
		Button( onClick = { } )
			{ 
				Text("Login")
			} 
		}

	A Composable function can call other composable functions.

	Example:
		@Composable 
		fun MainScreen() { 
			Header()
			Body() 
			Footer()
		}
	
	Responsibility :  Describe a reusable piece of UI that can participate in Compose Composition.

--> @Composable — basic meaning
	@Composable is an annotation used by Compose to identify functions that participate in the Compose composition model.

	Example:
		@Composable
		fun App() {
			Text("Hello")
		}


	Important:
		@Composable is not simply a normal annotation that means "this function is UI."
		The Compose compiler/plugin processes composable functions so that they can work with the Compose Runtime.

	Basic Flow:
		@Composable
				↓
		Compose Compiler
				↓
		Compose Runtime
				↓
		Composition / Recomposition


	Important Rules:
		A Composable Function can call another Composable Function.
		A normal Kotlin Function cannot directly call a Composable Function because it does not have a Compose composition context.
		
--> Composition
	Composition is the process in which Compose executes composable functions and builds the current UI structure described by them.

	Example:
		@Composable
		fun App() {
			Column {
				Text("Hello")
				Button(
					onClick = { }
				) {
					Text("Click")
				}
			}
		}

	Composition means:
		Building and managing the UI structure from Composable Functions.

	Important:
		Composition is NOT the same as drawing pixels on the screen.
		Composition determines and manages the structure of the Compose UI.
		Measurement, layout, and drawing are separate stages of rendering.


--> Composition Tree
	The Composition Tree represents the hierarchical structure created by composable functions during composition.

	Example:
		@Composable
		fun App() {
			Column {
				Text("Hello")
				Row {
					Text("Name")
					Button(
						onClick = { }
					) {
						Text("Save")
					}
				}
			}
		}

	Conceptually:
		App
		 ↓
		Column
		 ├── Text("Hello")
		 │
		 └── Row
			  ├── Text("Name")
			  │
			  └── Button
				   └── Text("Save")

	Think:
		Composable Functions
				↓
		Composition
				↓
		Composition Tree
		
	The Composition Tree allows Compose to keep track of the structure and relationships involved in the UI.

--> State
	State is data whose current value can change during the lifetime of the application and whose change can affect the UI.

	Example:
		count = 0				//Previous State

	After an action:	
		count = 1				//New State



	In Compose, observable UI state can be created using : mutableStateOf()

	Example:
		var count by remember {
			mutableStateOf(0)
		}


	Think:
		State = Current data that can affect the UI.

--> UI as a Function of State

	The fundamental Compose idea is:
		UI = f(State)

	Meaning:
		The UI shown by the application depends on the current State.

	Example:

		var count by remember {
			mutableStateOf(0)
		}

		Text("Count = $count")


	When:
		count = 0
		UI:
			Count = 0


		count = 1
		UI:

			Count = 1


	Think:

		State Changes
				↓
		Compose observes change
				↓
		Relevant UI is recomposed
				↓
		UI reflects new state

--> Relationship between State and UI

	State ≠ UI

	State	→	Data
	UI		→	Visual representation based on current State

	The developer changes the State.
	Compose observes the relevant state and updates the UI representation when necessary.
	
--> Recomposition
	Recomposition is the process where Compose re-executes relevant composable functions when observed state changes.

	Example:

		@Composable
		fun Counter() {

			var count by remember {
				mutableStateOf(0)
			}

			Button(
				onClick = {
					count++
				}
			) {
				Text("Count = $count")
			}
		}


	Initial:

		count = 0
		↓
		Text("Count = 0")


	User clicks Button:

		count++
		↓
		count = 1
		↓
		Recomposition
		↓
		Text("Count = 1")


	Important:

		Recomposition does NOT mean that the entire application is destroyed and rebuilt from zero.
		Compose uses information about the existing composition to determine which parts need to be re-executed.

--> How Compose builds UI

	At a simplified conceptual level:

		1. Application starts.
		2. Compose starts its runtime/composition.
		3. Root composable is executed.
		4. Root composable calls child composables.
		5. Compose records/manages the composition.
		6. UI is rendered on the screen.


	Example:

		App()
		 ↓
		LoginScreen()
		 ↓
		Column()
		 ├── Text()
		 └── Button()


	Compose uses this composable structure to manage the UI.

--> How Compose updates UI

	At a simplified conceptual level:

		State Changes 
			↓
		Compose detects the State change 
			↓
		Relevant Composable Functions are scheduled for Recomposition
			↓ 
		Composable Functions execute again as needed 
			↓ 
		Compose determines the required UI changes 
			↓ 
		Layout / Rendering is updated 
			↓
		UI reflects the new State


	Example:

		count = 0
				↓
		Text("Count = 0")

		User clicks
				↓
		count = 1
				↓
		Recomposition
				↓
		Text("Count = 1")
	
	Important: 
		"Only affected Composables execute again" is a useful simplified mental model. 
		In reality, Compose uses the Composition and compiler/runtime information to determine the scope of recomposition, and the exact amount of code re-executed can depend on the composition structure and state reads.

--> Compose Runtime — basic concept

	Compose Runtime is the underlying runtime system that manages the composition and state-driven UI updates.

	It provides the mechanisms needed for concepts such as:
		Composition	|	State Observation	|	Recomposition	|	Remembered Values	|	Composition Management


	Think:

		Composable Functions 
			↓
		Compose Compiler 
			↓
		Compose Runtime
			↓
		Composition 
			↓
		State Changes
			↓
		Recomposition 
			↓ 
		UI Update


	Important:

		Compose Runtime is not the same thing as the UI components themselves.

		Runtime manages the composition model.

		UI libraries provide components such as : Text | Button | Column | Row | Box

********************************* A. COMPOSE SYNTAX & ANNOTATIONS *********************************
	
--> What is an Annotation?	
	An annotation is metadata[Data about Data].
	It provides extra information about a program element.	It does NOT change the actual code.
	
		Example :
		
			@Composable
			fun App() {
			}
			The function is still a normal Kotlin function.	
			The annotation only provides additional information.
	
	--> Why do we need Annotations?

		Without Annotations, the Compiler or Framework would not know that something requires special processing.
		Annotations allow us to mark code with additional information.
	
	--> Who Reads The Annotation?
		• Kotlin Compiler	|	• Compose Compiler Plugin	|	• Compose Runtime	|	• IntelliJ IDEA		|	• Android Studio	|	• Libraries
		
	--> Is Annotation Executable Code?
		NO.
		An Annotation is NOT executable code.
		It is only additional information attached to a program element.
		
	--> Is Annotation A Kotlin Feature?
		YES.
		Annotations are a built-in Kotlin language feature.
		
		We can even create our own Annotation.
		Example :
			annotation class MyAnnotation

		Usage :
			@MyAnnotation
			fun greet() {

			}
	--> Common Kotlin / Compose Annotations

	Examples :
		@Composable	|		@Preview	|		@Deprecated	|		@Suppress	|		@Test

	Every Annotation has a specific purpose.		

	
--> @Composable
	`@Composable` is an annotation used to mark a function as a Composable function.
	Example :
		@Composable
		fun Greeting() {
			Text("Hello")
		}
	The function is still a normal Kotlin Function, but @Composable makes it participate in the Compose composition model.
	
	 The Annotation tells Compose :
        "This Function participates in the Compose UI system  and can be used during Composition."

	--> Why do we need @Composable?
		Without @Composable, Compose treats the Function as a normal Kotlin Function.It cannot participate in Composition.
		Compose does NOT recognize it as UI.

	--> What happens after adding @Composable?
		 The Compose Compiler Plugin processes Composable functions as part of the Compose compilation process.
		Flow :
			@Composable	->	Compose Compiler Plugin	->	Transforms the Function	->	Kotlin Compiler	->	Bytecode (.class)	->	JVM Executes	->	Compose Runtime uses it during Composition
	
	--> Is @Composable executable code?
		NO.
		`@Composable` itself is an Annotation. It does not contain the UI implementation.
		It provides information that allows the Compose compiler and Compose runtime system to treat the function as a Composable.
	
	--> Who processes @Composable?

    The Compose compiler/plugin processes Composable functions during compilation.

    The Compose runtime then manages their participation in Composition and Recomposition.

    Conceptually :
        @Composable	->	Compose Compiler	->	 Compose Runtime	->	 Composition / Recomposition
	
	Important rules:
		A Composable function can call another Composable function.
		A normal Kotlin function cannot directly call a Composable function.
		@Composable is read by the Compose compiler/plugin to treat the function as part of the Compose UI system.
	
	--> Composable Function Parameters

		A Composable function is still a Kotlin function, so it can have normal Kotlin function parameters.

		Example :
			@Composable
			fun Greeting(name: String) {
				Text("Hello $name")
			}

		Calling :
			Greeting("Rahul")
			
	--> Multiple Parameters

		Example :

			@Composable
			fun UserInfo(
				name: String,
				age: Int
			) {
				Text("$name is $age years old")
			}

		Calling :
			UserInfo(
				name = "Rahul",
				age = 28
			)

		Parameter syntax is normal Kotlin syntax.
	
	--> Reusable Composable Functions

    A Composable function can represent a small, meaningful, reusable part of the UI.

    Example :
        @Composable
        fun LoginButton() {
            Button(
                onClick = {}
            ) {
                Text("Login")
            }
        }

    We can call :
        LoginButton()

    We can also make the Composable configurable.

    Example :
        @Composable
        fun LoginButton(text: String) {
            Button(
                onClick = {}
            ) {
                Text(text)
            }
        }

    Then :
        LoginButton("Login")
        LoginButton("Sign In")
        LoginButton("Continue")
		
		
--> @Preview
	`@Preview` is an Annotation used by supported Compose development tools to display a preview of a Composable.
	It tells the IDE to render a preview of a Composable without running the entire application.
	@Preview is added when we want a development-time preview.
	
	Example :
		@Preview
		@Composable
		fun LoginScreen() {

		}


********************************* B. MODIFIER *********************************

--> Modifier
	A `Modifier` is an object used to describe changes to a Composable's appearance, layout, position, interaction, or behavior.
	It does NOT create UI.
	It modifies existing UI.
	
	Example : 
		 Text(
			text = "Hello",
			modifier = Modifier
				.padding(16.dp)
		)
	
	Meaning :
		Create Button
				↓
		Apply Modifier
		We can use it like :
			Modifier
				.padding(...)					//Add padding.
				.background(...)				//Draw a background.
				.fillMaxSize()					//Occupy all available space.
				
	--> Why Modifier?

	Instead of giving every UI Component dozens of parameters,
	Compose groups common UI modifications into one object called Modifier.
	
	--> Modifier is commonly passed to a Composable through a modifier parameter
		Here:
			modifier = Modifier.padding(16.dp)

	--> Reusable Composable

		When creating our own Composable, it is a good practice to expose a `modifier` parameter when the caller may need to control its layout or appearance.

		Example:
			@Composable
			fun UserName(
				name: String,
				modifier: Modifier = Modifier
			) {
				Text(
					text = name,
					modifier = modifier
				)
			}

		Now the caller can decide how the Composable should be modified.

		Example:
			UserName(
				name = "Rahul",
				modifier = Modifier.padding(16.dp)
			)
	--> Method Chaining
		Each function returns another Modifier, allowing the next function to be chained.
	
		Example :
			Modifier
				.padding(...)
				.background(...)
				.fillMaxSize()
				
		Conceptually :
			Modifier means Start with an empty Modifier.
			Then :  
				Modifier.padding(16.dp)	
					means : Create a new Modifier that includes padding.
			Then:
				Modifier
					.padding(16.dp)
					.fillMaxSize()
					
					means Take the previous Modifier and add another modification.
					
	--> Modifier Order
		The order in which Modifier operations are written can affect the resulting UI.

		Example:
			Modifier
				.padding(16.dp)
				.background(Color.Blue)

		is not always equivalent to:

			Modifier
				.background(Color.Blue)
				.padding(16.dp)

********************************* D. STATE BASICS *********************************		

NOTE :
	Compose follows Declarative UI.

		The Developer changes the State.
					↓
		Compose automatically updates the UI.

	State Management in Compose mainly consists of :
		• mutableStateOf()	|	• remember()|	• by (Property Delegation)

	These work together to manage and update UI State.	

--> mutableStateOf()				- it notify when something change then Recomposition happen and compose get new value
	
	Creates a State Object with an initial value.
	`mutableStateOf()` creates an observable Compose State object containing a value.

	Example:
		val count = mutableStateOf(0)
			 ↓						↓
    State object				Initial value		 
				
	--> Purpose
		Create a State Object that can notify Compose when its value changes.		.
		A normal Int is just a value and cannot notify Compose.

	--> Why not use a normal variable?
		
		Normal Variable :
			var count = 0
			count++
		Compose does not automatically observe an ordinary variable as Compose State.

		Therefore, changing it does not by itself tell Compose:
			"The UI needs to be reconsidered."
		
	--> With Compose State:

		val count = mutableStateOf(0)

		count.value++					//The state object's value changes.
		
		Compose can observe this state when it is read by Composable code and schedule the relevant recomposition.

	--> Accessing the Value
		
		mutableStateOf() returns a State Object.

		Read Value   : count.value

		Update Value : count.value++
		
--> remember()
	remember() stores an Object and returns the same Object during every Recomposition.	
		
	--> Problem without remember()

		Without remember()
		
			@Composable
			fun Counter() {
				val count = mutableStateOf(0)
			}
			
		A Composable can be executed again during recomposition.

		If we simply create the State object inside the Composable,we don't want a completely new State object to replace the
		previous one every time the function is recomposed.
		This is where `remember()` is used.

	Solution : remember()
		`remember()` stores a value in the Composition and returns the remembered value across recompositions.
		
		@Composable
		fun Counter() {

			val count = remember {
				mutableStateOf(0)
			}
		}


	--> What does remember() remember?

		`remember()` remembers the result produced by its lambda.
			Example :
				remember {
					mutableStateOf(0)
				}
			The lambda returns a State Object.
			So remember() remembers the State Object, not the integer value.

--> remember() + mutableStateOf() 

	--> Why are they used together?
			mutableStateOf()	->	  Creates observable State
			remember()			->	Keeps that State associated with the Composition across recompositions
		
		Together:
			
			remember {
				mutableStateOf(0)
			}

			gives us State that survives recomposition.
		
	--> Example
		@Composable
		fun Counter() {

			val count = remember {
				mutableStateOf(0)
			}

			Button(
				onClick = {
					count.value++
				}
			) {
				Text("Count = ${count.value}")
			}
		}

	Flow:
		Initial State	->	 count = 0		->	UI shows "Count = 0"	->	User clicks Button	->	count changes to 1	->	 Compose observes State change	->	Recomposition	->	 UI shows "Count = 1"
		
-->  by (Property Delegation in Compose) 

	--> Without by :
			val count = remember {
				mutableStateOf(0)
			}
			Read	→	count.value
			Update	→	count.value++
			
	--> With by :
			var count by remember {
				mutableStateOf(0)
			}
		Read	→	count
		Update	→	count++

	--> Purpose
		by automatically accesses .value.
		It makes the code shorter and easier to read.
		
	Note : 
		Use val when working without "by"
		Use var when using by because the value itself changes.
		
		Example :
			var count by remember {
				mutableStateOf(0)
			}

				The delegated property itself is being read and assigned:

					count++
					count = 10

				Therefore we use `var`.

			Without `by`, the state-holder reference can remain `val`:

				val count = remember {
					mutableStateOf(0)
				}

				count.value++

--> rememberWindowState()
	`rememberWindowState()` is a Desktop Compose helper used to create and remember a `WindowState`.
	
	Example:
		Window(
			state = rememberWindowState()
		) {
			App()
		}
	
	--> What is WindowState?
		`WindowState` represents the state/configuration of a desktop window, such as:
			• Width	|	• Height	|	• Position	|	• Placement(Normal / Maximized / Fullscreen)
			

	--> Important
		WindowState ≠ Native Window
		WindowState stores information about the window.
		It does NOT itself create the native desktop window.
				
	--> Why rememberWindowState()?
		`rememberWindowState()` remembers the WindowState across recompositions instead of creating a replacement state object each time.
		
		Example:
			Window(
				state = rememberWindowState(
					placement = WindowPlacement.Fullscreen
				)
			) {
				App()
			}
		
		Meaning :
			Create one WindowState object
					↓
			Initial Placement = Fullscreen
					↓
			Remember the same WindowState object across Recompositions.

			
	--> Why not use remember { WindowState() }?

		Because creating and remembering WindowState is a very common requirement.
		Compose provides a helper function :	rememberWindowState()

		• Normal	|	• Maximized		|	• Fullscreen

	--> rememberWindowState()
		`rememberWindowState()` creates and remembers a WindowState across recompositions.

		Example :
			Window(
				state = rememberWindowState(
					placement = WindowPlacement.Fullscreen

			) {

			}
		--> Why rememberWindowState()?
			WindowState is state associated with the Compose window.
			During recomposition, we do not want to replace the state object unnecessarily.

			`rememberWindowState()` keeps the WindowState associated with the current Composition.

			Important :
				`rememberWindowState()` remembers the WindowState.

********************************* F. APPLICATION CONFIGURATION *********************************
--> application()
	`application()` is a Compose Desktop application function that provides the application environment and desktop application lifecycle.	
	
	Example :
		fun main() = application {
			Window(
				onCloseRequest = ::exitApplication
			) {
				App()
			}
		}
		
	--> Relationship with main()
		`main()` is still the Kotlin/JVM entry point.
		`application()` is called from `main()` to start the Compose Desktop application environment.

	--> application() is a Higher-Order Function
		`application()` accepts a lambda.

		Example :
			application {
				Window(...) {
					App()
				}
			}

		The code inside `{ }` is the lambda passed to application().

		Conceptually :
			application(
				content = {
					Window(...) {
						App()
					}
				}
			)
--> application() Parameters
	The important parameters we need to know here are :
		1. content	|	2. exitProcessOnExit
	
	1. content (Lambda)
		`content` is the lambda containing the code that should run inside the Compose Desktop application environment.
		Example:
			application {
				Window(
					onCloseRequest = ::exitApplication
				) {
					App()
				}
			}
		Conceptually :
			application()	->	Compose application environment	->	content lambda	->	Window()	->	App()
	
	2. exitProcessOnExit
		Purpose : Controls whether the JVM Process exits when the Compose application closes.
		Example :
			application(
				exitProcessOnExit = true
			) {
				Window(
					onCloseRequest = ::exitApplication
				) {
					App()
				}
			}
		Default :   true
			 Application exits
				  ↓
			JVM process exits
			
		`false` :
			Application exits
				  ↓
			JVM process is not automatically terminated by this setting

******************************************** Chapter 5 - Build Lifecycle ********************************************
Build Lifecycle is the complete process from clicking the Run button until the application is displayed on the screen.

--> Complete Build Lifecycle 

	Click Run	->	Gradle Starts	->	Read settings.gradle.kts	->	Read build.gradle.kts	->	Download Plugins	->	Download Dependencies	->	Configure Plugins
																																								|
																																								|
																																								↓
	Load Application Classes 	<-	 JVM Startup 	<-	 Package Application 	<-	 Generate JVM Bytecode (.class)	<-	 Compose Compiler Plugin	<-	 Compile Kotlin
		|
		|
		↓
	main()	->	application()	->	Compose Runtime Starts	->	Window()	->	Operating System Creates Native Window	->	Composition	->	Composable Functions Execute	->	UI Displayed


--> Click Run	:	When the Run button is clicked, IntelliJ IDEA starts the Gradle Build Process.

--> Gradle Starts	:	Gradle becomes responsible for building and running the project.
		Responsibilities : Read Build Configuration | Download Required Components | Compile Source Code | Package Application | Run Application

--> Read settings.gradle.kts	:	Gradle first reads settings.gradle.kts.
		Purpose :	Identify Root Project	|	Configure Plugin Management	|	Locate Plugin Repositories

--> Read build.gradle.kts	:	Gradle now reads build.gradle.kts.
		Purpose :	Load Plugins	|	Configure Kotlin	|	Configure Compose	|	Configure Repositories	|	Configure Build

--> Download Plugins	:	If required Plugins are not available, Gradle downloads them.
		Examples :	Kotlin Multiplatform Plugin	|	Compose Multiplatform Plugin

--> Download Dependencies	:	Gradle downloads project Libraries.
		Examples :	Compose Runtime	|	Coroutines	|	SQLite	|	Retrofit	|	Ktor

--> Configure Plugins	:	After downloading, Gradle initializes every Plugin.
		Examples :	Kotlin Plugin	|	Compose Plugin

--> Compile Kotlin	:	Kotlin Compiler converts	:	.kt Files	->	JVM Bytecode	->	.class Files

--> Compose Compiler Plugin	:	The Compose Compiler Plugin extends the Kotlin Compiler.
		Purpose :	Process @Composable Functions.	->	Generate additional Compose-specific code.

--> Generate Bytecode
		Result of Compilation :	.class Files
		Bytecode is understood by the JVM, not by the Operating System.

--> Package Application	:	Gradle packages everything together.
		Application Package contains : .class Files	|	Kotlin Runtime	|	Compose Runtime	|	External Libraries


--> JVM Startup	:	Gradle starts the JVM.
		JVM Responsibilities : Load Classes | Allocate Memory | Execute Bytecode

--> Load Application Classes	:	The JVM loads all required .class files into memory.
		Examples :	MainKt.class	|	Compose Classes	|	Application Classes

--> main()	:	The JVM starts execution from	main()	This is the Entry Point of the application.


--> application()	:	main() calls	application()
		Purpose :	Start the Compose Runtime.Create the Compose Environment.

--> Compose Runtime Starts	:	The Compose Runtime becomes responsible for - 	• Composition	|	• State Management	|	• Recomposition	|	• UI Rendering


--> Window()	:	application() executes	Window()
		Window()
			↓
	Requests the Operating System
			↓
	Create a Native Window

--> Operating System Creates Native Window
		The Operating System creates the actual Desktop Window.
		Compose does NOT create the Window.	It requests the Operating System to create it.

--> Composition
		Compose executes every Composable Function.
			Examples :	App()	|	MainScreen()	|	Button()	|	Text()
		Compose combines them into one UI Tree.

--> UI Displayed
		After Composition completes, the UI is rendered inside the Native Window.
		The application is now ready for user interaction.

************************************************ Chapter 6 - State Management ************************************************

--> State :
	Data that can change while the application is running.
	Example :	Counter Value	|	Username	Password	|	Login Status	|	Selected Item	|	Dark Mode
	
--> remember()

	Purpose :	Store a value in Compose memory.
	Syntax	:	
		remember {
			Initial Value
		}

	Example	:
		val count = remember { 0 }

	Problem Solved :
		Prevents values from being recreated during Recomposition.

	Limitation
		remember() does NOT notify Compose when the value changes.

	Note	:	remember() remembers a value.  It does not make the value observable.
	
--> mutableStateOf() 
	Purpose 		:	Create an observable State object.
	Syntax			:	mutableStateOf(0)

	Return Type		:	MutableState<T>
	
	Example			:	val count = mutableStateOf(0)

	Read Value		:	count.value

	Update Value	:	count.value++

	Responsibilities :	Store the value.	|	Allow the value to change.	|	Notify Compose when the value changes.

	Difference		:
		remember()			:	Keeps the State object alive.
		mutableStateOf()	:	Makes the value observable.

	Flow	:
		count.value changes		->	 Compose notified	->	Recomposition	->		UI Updated
		
--> by (Property Delegation)
	
	Purpose :	Remove the need to use .value when working with MutableState.

	Without by	:	
		var count = remember {
			mutableStateOf(0)
		}

		Read 	:	count.value
		Update 	:	count.value++

	With by	:
		var count by remember {
			mutableStateOf(0)
		}

		Read 	:	count
		Update	:	count++


	Required Import:
		import androidx.compose.runtime.getValue
		import androidx.compose.runtime.setValue

	Note :
		by delegates reading and writing to the underlying MutableState object.
		It is Kotlin's Property Delegation feature, not a Compose feature.
		
--> Recomposition

Purpose :	Re-execute Composable functions when State changes.

Flow	:	State Changes	->	Compose detects the change	->	Recomposition starts	->	Affected Composable functions execute again		->		UI is updated

Example	:	
		count++
            ↓
    mutableStateOf detects the change
            ↓
    App() executes again
            ↓
    Text("Count : $count")
            ↓
    Screen updates

Note :
    During Recomposition,
        • State values are preserved by remember().
        • Only Composable functions depending on the changed State are recomposed.
        • The entire application is not recreated.
		
************************************************ Chapter 7 - Modifier & Layout Mastery ************************************************

--> Modifier Chain
	
	Purpose :	Apply multiple Modifiers to a Composable.

	Example	:	Modifier.fillMaxWidth().background(Color.Yellow).padding(16.dp)

	Execution Order	:	Modifier	->	fillMaxWidth()	->	background()	->	padding()

	Note :

		• Modifiers are applied in the order they are written.
		• Changing the order can produce a different UI.
		
--> padding()

	Purpose :	Adds spacing around a Composable.
	Syntax	:	Modifier.padding(16.dp)

	Example	:
		Modifier
			.background(Color.Red)
			.padding(16.dp)

	Behavior :
		background()
			↓
		Draws the background.

		padding()
			↓
		Adds spacing around the previous result.in between text and background

	Example
		background()
			↓
		padding()

		Result :	Red background with spacing around the Text.

	Note
		• padding() creates spacing.
		• It does not change the Text size.
		• Modifier order affects the final UI.
		
--> size() 

	Purpose :	Sets both Width and Height of a Composable.

		• size() changes the Composable size.
		• It does not change the content size.
		• Width and Height become equal.

		)

		• Width remains unchanged.
		• Only Height changes.
